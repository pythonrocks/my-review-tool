# Architecture

Endpoints, output format, saved results, safety, release and tests. For the product background see [Project overview](project-overview.md).

## Endpoints

- `GET /` — dashboard page (HTML titled "myReview"), kept current by live refresh (see Live refresh below). It shows:
  - `Signed in to GitHub as <login>` at the top, naming the `gh` account used; omitted until the login is known or when fetching it fails;
  - a `Settings` link at the top right (see [First launch and Settings](configuration.md#first-launch-and-settings));
  - the watched repositories, each linked to its GitHub page, or an `Add repositories in Settings` link when the list is empty. A repository whose last fetch failed shows the error inline (`owner/name — error: <message>`); its last good pull request list stays in the table until a fetch succeeds again;
  - when `gh` is not installed or not logged in, that message above the list, with how to fix it; per-repository errors are hidden while it is shown;
  - the open pull requests of all watched repositories in one table (⭐ (Review requested): ⭐ labelled `Your review is requested` when the PR requests your review, directly or through one of your teams, Repository, with the org above the repository name, Pull request linked to GitHub, Author, Age such as `45m`, `3h`, `2d`, `draft` for drafts, and Approved: ✅ when you approved the PR and 👥 when others did, both possible with yours first, labelled `Approved by me` or `Approved by alice, bob`; an approval of an older commit than the head shows the same symbol dimmed with a dashed outline, labelled `Approved by me on an older commit`, `Approved on an older commit by carol`, or `Approved by alice, bob; on an older commit by carol` when others' approvals are mixed, and 👥 is dimmed only when every other approval is outdated; until the `gh` login is known every approval counts as others'), in the order described under Dashboard order below. Before the first poll finishes it shows "Loading pull requests…", and "No open pull requests." when there are none;
  - a Review column with the status of the PR's review workflow (see [Review workflow](user-guide.md#review-workflow)). A done review shows the four severity circles, always in the order Critical, High, Medium, Low, with the count inside (code and security review findings combined); a severity with no findings shows a muted circle with `0`; the text moves into the tooltip and screen-reader label, for example `Review done: 1 critical, 2 high, 0 medium, 3 low`. Other statuses are text badges: `queued`, `running`, `failed: <step>: <reason>`, `skipped` (the full `skipped: <reason>` in its tooltip, see [Skip rules](configuration.md#skip-rules)), `on demand` for a PR older than `auto_review_max_age` with no saved result (tooltip `on demand: created more than 168h0m0s ago`), and `not queued` while the queue does not know the PR yet (until the poll that found it has been handed to the queue). When the result is for an older commit than the PR's current head, a failed status is prefixed with `outdated: ` (for example `outdated: failed: code review: <reason>`) and a done review shows an `outdated` badge before its circles, labelled for example `Outdated: review done: 0 critical, 1 high, 0 medium, 2 low`;
  - Risk and Recommendation columns after Review, filled only for a done review, outdated or not (see [Risk assessment](user-guide.md#risk-assessment)): Risk is a three-step meter (one green, two amber or three red bars) labelled `Risk: High`, `Risk: Medium` or `Risk: Low`; Recommendation is an amber **!** labelled `Human review required` or a green **✓** labelled `Automated review is sufficient`. Each indicator's label is both its hover tooltip and what a screen reader reads;
  - a `Details` link styled as a small button (to `/pr/<owner>/<name>/<number>`) and a `Re-run` button in the last column of every row, whatever the status except skipped, labelled `Review` for an on-demand PR; Re-run posts to `/rerun`; with JavaScript it updates that row in place (see Live refresh), without it the page reloads at the same URL, keeping the active filters;
  - above the table, a filter form (a plain `GET` form to `/`, see Dashboard filters below) and, while any filter is active, `Showing X of Y pull requests, Z hidden by filters.`, then one removable chip per active value (in the order org, repo, author, each risk, each rec, mine, hideskipped, hideapproved; for example `Risk: Low ×`, labelled `Remove filter Risk: Low`, linking to `/?<filters>` without that one value, or `/` when it was the only one; an unknown value gets a chip too), then a `Clear filters` link to `/`. Chips and `Clear filters` are plain links (full page loads), so the form always matches the list. When pull requests exist but none match it shows "No open pull requests match the filters.", or "No open pull requests request your review." when Requested (`mine=1`) is the only active filter.

  Dashboard filters (query parameters of `GET /`; live refresh keeps them):

  | Control | Parameter | Values |
  | --- | --- | --- |
  | Org select (All orgs) | `org` | empty (All orgs) or one owner |
  | Repository select (All repos) | `repo` | empty (All repos) or one `owner/name` |
  | Author select (All authors) | `author` | empty (All authors) or one login as the Author column shows it (bots as `app/<name>`) |
  | Risk segments: Low, Medium, High (with the risk meter) | `risk`, repeatable | `Low`, `Medium`, `High` |
  | Recommendation segments: **!** (Human review required), **✓** (Automated review is sufficient) | `rec`, repeatable | `human`, `automated` |
  | Requested ⭐ chip (Only PRs requesting my review) | `mine` | `1` |
  | Hide skipped chip | `hideskipped` | `1` |
  | Hide approved chip (Hide approved by me) | `hideapproved` | `1` |

  The bar is one wrapping row. The selects have visually hidden labels; Risk and Recommendation are fieldsets with a visually hidden legend; every segment and chip is a real (visually hidden) checkbox with its label, so it reports its state and works with Tab and Space.

  Instant apply: changing any control (or pressing Enter) sends the form with htmx and replaces only the list (`<div id="pr-rows">`: the counts line with the filter chips and `Clear filters`, the loading and empty messages, and the table); the form itself is not replaced. A `GET /` with the header `HX-Request: true` (and no `HX-History-Restore-Request`) returns only that list fragment, built by the same code as the full page, with `HX-Push-Url` set to `/?<filters>` re-encoded from the parsed filter parameters (the same rules as Re-run's redirect), or `/` when no filter is active, so the address bar shows the canonical query. Every `GET /` response sets `Vary: HX-Request`. Back/forward reloads the URL as a full page (`historyCacheSize` 0). The Apply button submits the form as a plain `GET`; `static/dashboard.js` hides it once htmx has loaded, so without JavaScript, or when htmx does not load, Apply stays visible and the filters work with full page loads.

  Live refresh: with JavaScript the page never reloads itself. The list fragment ends with a hidden poller (`<span id="pr-poll">`) that fetches `GET /?<filters>` (its own canonical query) into `<div id="pr-rows">` every 10 seconds while any visible row (after filters) is `queued` or `running`, or while "Loading pull requests…" is shown, and every 60 seconds otherwise; filtered-out rows do not count. Each refresh replaces the poller, so the interval is recalculated each time. A poll request (header `HX-Trigger: pr-poll`) gets no `HX-Push-Url`, so polling adds no history entries. Every list fragment (filter change and poll) also carries the global error and the "Watched repositories" section with its per-repository errors (`<div id="poll-status">`, as an htmx out-of-band swap), so they update with the rows from the same snapshot; the filter form is never replaced, so an open select, scroll position and focus survive a refresh (the Details link and Re-run button of each row have stable ids, `details-<owner>/<name>-<number>` and `rerun-<owner>/<name>-<number>`, so htmx restores focus to them). A poll is dropped while a filter request is in flight, and a filter change aborts a poll in flight. When a poll fails (server down) nothing is swapped and the rows stay. `static/dashboard.js` skips polls while the tab is hidden and refreshes at once when it becomes visible. Refreshes read only the in-memory poll results and review statuses; they make no GitHub calls. Without JavaScript, `<noscript><meta http-equiv="refresh" content="60"></noscript>` reloads the whole page every 60 seconds. In-place Re-run: with JavaScript, the Re-run button posts with htmx and replaces only its own row with the answer, which already shows `queued` (or `running`), and resets the poller to 10 seconds with the page's filters, so the row then follows the review without a reload; the row stays even if it no longer matches the filters until the next poll. A Re-run aborts a poll in flight (its older state is never swapped in) and is sent at once; a poll that starts while a Re-run is in flight is dropped, and a second Re-run waits for the first, so each row shows its own answer. A filter change aborts a Re-run in flight; the review is still queued and the new list shows it. When the Re-run fails (400, 404 for a PR that closed meanwhile, 409 for a skipped PR) the row is replaced by an error row with the message; the next poll restores or removes it. Focus stays on the Re-run button (stable id). Known limit: the Org, Repository and Author choices in the form are not refreshed by polling (refreshing the form would close an open select); a new repository or author appears there after a full reload or a filter change.

  The Org, Repository and Author choices are the distinct values of every PR on the dashboard, sorted case-insensitively. Filters combine with AND; the values of `risk` and of `rec` combine with OR. Rows keep the dashboard order. Other parameters are ignored, only the first `org`, `repo` and `author` value is used, an empty value means no filter, and for `mine`, `hideskipped` and `hideapproved` any value other than `1` means off. A value that is unknown or no longer on the dashboard (for example `risk=bogus` or a repository whose last PR merged) matches nothing, never an error; an unknown `org`, `repo` or `author` value is shown as an extra selected choice. Risk and Recommendation match only a done review (current or outdated) with that value, so they hide queued, running, failed, skipped and not yet queued PRs. Hide skipped hides PRs whose review is `skipped`. Hide approved by me hides PRs the `gh` login approved on the current head (an approval of an older commit does not hide the PR); until the login is known it hides nothing.

  Dashboard order: PRs requesting your review come first; each part is then ordered as below. Every ready PR comes before every draft, and each of the two is ordered by group:
  1. human review required (a done, current review), High risk before Medium;
  2. failed (a current failed review);
  3. automated review is sufficient (a done, current review);
  4. waiting for a review: queued, running, not yet known to the queue, and ready PRs with an outdated result (they are queued again after the quiet period);
  5. drafts with an outdated result, waiting for Re-run;
  6. on demand: older than `auto_review_max_age` with no saved result, waiting for Review;
  7. skipped by a [skip rule](configuration.md#skip-rules).

  Inside a group the oldest PR (by creation time) comes first, then repository and number. Rows move between refreshes as reviews finish.
- `GET /?mine=1` — the same page showing only the pull requests requesting your review, in the same order (the Requested filter above). Any other `mine` value means no filter.
- `GET /myreview.css` — the pages' stylesheet, embedded from `static/myreview.css` (dark by default, light when the browser prefers it). The pages load nothing else from other sites. JavaScript is limited to htmx, served locally from `/static/htmx.min.js`, the dashboard's small `/static/dashboard.js`, the details page's `/static/details.js` and the Settings page's `/static/settings.js`; the pages have no inline scripts or styles.
- `GET /static/htmx.min.js` — [htmx](https://htmx.org) 2.0.x, vendored as `static/htmx.min.js` and embedded in the binary, so it works offline and never loads from a CDN. `static/htmx.md` records its version, source URL, SHA-256 and license (0BSD). Both the dashboard and the details page load it (with `allowEval` off).
- `GET /static/dashboard.js` — embedded from `static/dashboard.js` (`text/javascript`), loaded by the dashboard after htmx. It adds the class `htmx-on` to `<html>` when htmx is running, which hides the filter form's Apply button, and pauses the list poller while the tab is hidden (see Live refresh).
- `GET /static/details.js` — embedded from `static/details.js` (`text/javascript`), loaded by the details page after htmx. Keys (ignored while typing in an input, textarea or select, and with Ctrl, Meta or Alt held): `j` / `k` move to the next / previous point (a list row or a diff block, line comments included), scroll it into view and open it; `c` opens the current point (the last one moved to or clicked, else the first) and focuses its comment textarea, after its body has loaded. The `← Previous` / `Next →` links also open their target, and the diff view's `Files with points only` checkbox hides the files (and their links) without points.
- `GET /settings` — the Settings page (see [First launch and Settings](configuration.md#first-launch-and-settings)); `?first=1` is the first-launch version (title `Welcome to myReview`, button `Save and start`, no back link). It renders from memory; the CLI checks load afterwards.
- `GET /static/settings.js` — embedded from `static/settings.js`: the prompt tabs (click, or arrow keys, Home and End on the focused tab) and the Remove buttons of the repository chips. Without JavaScript the three prompts are stacked and the connection checks do not run.
- `GET /settings/status/<gh|claude|codex>` — the status of one CLI as an HTML fragment (10 s timeout); any other name returns 404. On `?first=1`, the Codex fragment also swaps in (out of band) the agent choice with Codex selected when Codex is logged in and Claude is not.
- `GET /settings/prompt-default?step=<code_review|security_review|risk_assessment>` — the step's text box holding the built-in prompt; any other step returns 400.
- `POST /settings` — form fields `repo` (repeated), `agent` (`claude`, `codex` or empty to keep the per-step agents), `prompt_code_review`, `prompt_security_review`, `prompt_risk_assessment` and `first`. Saves and applies the config; on success 303 to `/`, or 200 with `HX-Redirect: /` for htmx. Any error answers 422 with the form (htmx) or the whole page, showing the message and the input as sent; the config is left unchanged.
- `GET /healthz` — JSON with `status`, `version`, the number of watched `repositories`, the number of open `pull_requests` held in memory, and `last_successful_poll`: the end time (RFC 3339, UTC) of the latest poll in which every repository was fetched without error, or `null` before the first one:

  ```json
  {"status":"ok","version":"0.1.0","repositories":2,"pull_requests":5,"last_successful_poll":"2026-11-12T20:15:00.123456Z"}
  ```

- `GET /pr/<owner>/<name>/<number>` — details page of a pull request on the dashboard (the same list, including the last good list kept while a fetch fails). From top to bottom:
  - a link back to the dashboard with the filters last used on it (`/?<filters>` from the latest dashboard request since the app started, kept in memory only; `/` when none were active); `<owner/name> #<number> <title>`; Author, Age, Draft (`yes`/`no`), Reviewed `<short sha>` (the reviewed commit, only when a done or failed result exists), the review status badge (`done` or `outdated: done` for a done review, whose counts are in the decision bar; otherwise the dashboard's text, such as `queued` or `failed: <step>: <reason>`) and Approvals from the last poll with the dashboard's wording (`Approved by me; approved by alice, bob; on an older commit by carol`, or `none`); on the right "Open on GitHub ↗" and a `Re-run review` button that returns to this page (not for a skipped PR; labelled `Review` for an on-demand PR);
  - the **update banner** (`#update-slot`, `role="status"`), in every review state: every 15 seconds it asks the status endpoint below and shows its answer; the page itself never reloads, so typing is never interrupted. It shows `New review results for commit <short sha>. Your N edited drafts will be kept; M untouched suggestions will be replaced.` with a `Reload review` button, and so on (see the status endpoint);
  - for an outdated result: `These results are for commit <reviewed sha>; the pull request is now at <head sha>.` (7-character SHAs), followed by `A new review is queued <quiet_period> after the last push.` for a ready PR (the configured value, such as `5m0s`; the page does not reload itself, so a comment being edited is kept) or `Draft: click Re-run to review the new commits.` for a draft; then, after a submitted review, `Review submitted: <Approved|Changes requested|Commented>, N comments.` (from `?submitted=<event>&n=<count>`; an unknown event or a count that is not a non-negative integer shows nothing);
  - the **decision bar**, which stays at the top while scrolling. For a done review: the recommendation (`Human review required` or `Automated review is sufficient`), the risk badge (`<High|Medium|Low> risk`), the counts (findings of both steps by severity, non-zero only, Critical to Low, such as `1 high, 2 low findings`, `1 low finding` or `No findings`; `N point(s) of interest` as listed below; `N security finding(s)` or `no security findings`), the progress `N of M checked` (checked rows of the M rows listed below) and the first two rationale lines that do not start with `Risk ` (that line restates the verdict). For other states it holds `Review not queued yet.`, `Review queued.` or `Review running.`, `Review failed at <step>: <reason>.`, `skipped: <reason>` or, for an on-demand PR, `Not reviewed automatically: created more than <auto_review_max_age> ago. Click Review to start it.`. On the right are the decision radios `Approve`, `Request changes` and `Comment` (default; on your own PR, when the `gh` login equals the author ignoring case, only `Comment`) and `Submit review (N)`, N being the rows whose comment is in the pending review; it opens the submit dialog for the chosen decision (see [Submitting a review](user-guide.md#submitting-a-review)). Every review state has these controls; only a done review has the progress and drafts. Below them, `Approving needs confirmation:` with the lines an approval must confirm. A done, current, Low-risk review with nothing to confirm and no comment in the review gets a one-line compact bar without reasons, with a `Comment or request changes…` link that opens the dialog and an `Approve` button that submits an approval at once, without the dialog (not on your own PR). Errors of checking, saving and Add/Remove appear at the bottom of the bar. `You approved commit …` and `Could not check your approvals…` appear right below the bar. The verdict and the risk level appear only in the bar;
  - the view switch: "What to check" (`?view=list`, with the number of items) and "Diff" (`?view=diff`). The first `view` value counts; a missing, empty or unknown value shows the list (200). The diff view is described under [Diff view](user-guide.md#diff-view);
  - the list view, for a done review only: **Context**, the code review's summary clamped to two lines, with a "Show more"/"Show less" toggle (no JavaScript) when it has more than two lines or 240 characters, or `No overview.`; one line `Severity threshold <threshold> (<source>) · Sensitive areas: <names, comma-separated, or none> (<source>)`, where the source is `repository policy` or `default` (see [Repository policy](configuration.md#repository-policy)); then the AI metrics line (below); then **What to check**, one numbered list: every finding of the code and security reviews sorted Critical, High, Medium, Low, then by file and line, then the points of interest in the order the decision computed (see [Risk assessment](user-guide.md#risk-assessment)), without the points generated from a finding (same file, line and `<Severity> <step> finding: <description>` reason). Each row shows its number, the severity badge or `Point`, its title, and `file:line` (`file` when there is no line) and expands (a `<details>` element, so without JavaScript too) to a line with the step (`Code review` or `Security review`, findings only) and an info icon whose tooltip (on hover or keyboard focus; Escape hides a focused one) holds the full description of a finding or the full reason of a point, and, except on a posted row, a restore icon whose tooltip holds the suggested comment as plain text (not rendered as Markdown) and which puts that comment back into the editor (JavaScript). Then come the location linked to the file at the reviewed commit, `https://github.com/<owner>/<name>/blob/<sha>/<file>#L<line>` (no `#L` for line 0; it can differ from the PR's current head after a newer push), and the comment editor, pre-filled with the suggested comment (see [Checked marks and comment drafts](user-guide.md#checked-marks-and-comment-drafts)). Each row also has a checkbox before its number and a state badge (`Suggestion`, `Edited`, `Draft`, `Draft edited` or `Posted`) before its chevron. A row whose title or suggested comment is empty (an agent left it blank, or the result was saved before these fields existed) shows instead the first non-empty line of the description or reason as the title (whitespace collapsed, cut to 80 characters with `…`), and the description or reason as the suggested comment, in the restore icon's tooltip and the editor. With JavaScript, opening a row the first time reloads its body from the point endpoint below. A review with no findings and no points shows `Nothing to check: no findings and no points of interest.`
  - the AI metrics of a done review (below the policy line) or a failed one (below the tabs), when its result has `metrics` (see [Saved results](#saved-results); older results show nothing): one muted line `AI review: <cost> · <time> · <models> · <tokens> tokens`. Time is `finished_at − started_at`, models are every step's model names, tokens are input, output and cache tokens summed over the steps that reported. The cost is the sum of the priced steps (`$0.42`, `<$0.01` below half a cent), plus ` + codex (no price)` when codex steps ran, plus ` + unknown` when a step has no report; `no price` when only codex steps ran and `unknown` when no step is priced and one has no report, never `$0.00` for an unknown cost. Below it, a collapsed **Run details** (`<details>`, no JavaScript) table: Step, Agent, Model, Time, API time, Turns, Tokens in, Out, Cache read, Cache write, Cost (est.: `$0.12`, `no price` or `unknown`) and Result (`N findings`, or the failure reason), with `—` for values the agent did not report; then `Queued 12s · Attempt 2 · Diff 14 files, 38 KiB`. Durations read `850 ms`, `12s`, `1m 05s` or `1h 02m`, and tokens `950`, `23.7k` or `1.2M`.

  Each load asks GitHub, with `gh`, for your reviews of the PR. Summary, descriptions, rationale, reasons and all PR text are shown as plain text (line breaks kept, never Markdown). An unknown repository or number, a non-integer number, or any request before the first poll returns 404.
- `GET /pr/<owner>/<name>/<number>/status?results=<id>&head=<sha>&view=<list|diff>` — the update banner of a details page that shows the results `<id>` (the page's `<body data-results>`) of the PR at head `<sha>`. It reads only memory and the pending file: no `gh` call, no write. For a done result whose id differs from `results`: `New review results for commit <short sha>. Your N edited drafts will be kept; M untouched suggestions will be replaced.` (N: unposted drafts that are edited or line comments; M: the rows of the results the pending review was last reconciled with, minus its unposted edited finding and point drafts, at least 0; `1 edited draft`, `1 untouched suggestion` in the singular), or `New review results for commit <short sha> were loaded in another tab.` when the pending review is already reconciled with them. For a failed result whose id differs: `The review of commit <short sha> failed at <step>: <reason>.` These three end with `Reload review` (`id="reload-review"`), a form that htmx posts with `view` to `…/reload`; its errors (404, 500) show in the page's alert row (`#pending-error`), as do the details page's Re-run errors (404, 409), through `static/details.js`. Otherwise, when `head` is not the PR's head: `PR updated to <short head>; click Review to review it.` for an on-demand PR, `PR updated to <short head>; not reviewed (skipped by rule skip[<n>]).` for a skipped one, `PR updated to <short head>; Re-run to review it.` for a draft PR, and `PR updated to <short head>; review queued.` otherwise, without a button. Otherwise (same results and head, or a queued or running review) 204, which swaps nothing. A PR not on the dashboard returns 404.
- `POST /pr/<owner>/<name>/<number>/reload` — form field `view`. Reconciles the pending review with a done result (see [Checked marks and comment drafts](user-guide.md#checked-marks-and-comment-drafts); never for a queued, running or failed one) and redirects with 303 to `/pr/<owner>/<name>/<number>?view=<list|diff>` (any other `view` means `list`); an htmx request (the page's Reload review button) gets 200 with `HX-Redirect` to the same URL instead. A PR not on the dashboard returns 404, a failed write 500. A full `GET` of the details page reconciles the same way (500 when the write fails), so a new tab or F5 is a reload too.
- `GET /pr/<owner>/<name>/<number>/points/<id>` — the expanded body of one "What to check" row as an HTML fragment (`text/html`, 200). `<id>` is `f<i>`, the finding at index `i` of the result, or `p<i>`, the point of interest at index `i`. An unknown PR, a non-integer number, a review that is not done, a malformed id (a line comment id included) or an index out of range returns 404. The body loads the code excerpt below (`hx-trigger="load"`, after the text) and ends its links with `← Previous` / `Next →` to the neighbouring rows of the list (`#pt-<id>`; `#d-<id>` with `?view=diff`), none at the ends. Only bodies shown open load an excerpt, so a page load reads no files.
- `GET /pr/<owner>/<name>/<number>/points/<id>/excerpt` — lines `L-3..L+3` (clamped to the file) of the item's file at the reviewed commit, read with the same `gh api …/contents/…` call as Expand, as `.code .dl` rows with new-side numbers and no +/− signs; line `L` has the class `focus`. It reads the file, not the diff, so it works for items outside the diff and for outdated results, and never lists the PR files. Line 0, a file path from the agent that is not a safe relative path (empty, over 1024 bytes, invalid UTF-8, control characters, `\`, a leading `/`, or an empty, `.` or `..` segment), a missing or binary file, a file over 1 MiB, `L` past the end of the file, or a `gh` error answer 200 with `Code excerpt not available`. The id rules of the point endpoint apply (404).
- `GET /pr/<owner>/<name>/<number>/diff/comment-form?path=<file>&line=<n>` — for a new-side diff line: the editor of your line comment there, if there is one, else a form (hidden `path` and `line`, a textarea, `Add comment`) that posts to `…/drafts`. The diff inserts it after the line, once per line per page load. `path` and `line` are checked as for Expand (404 for a path, 400 for a line that is not a context or added line of a hunk); a review that is not done for the PR head returns 409, a `gh` error 502.
- `POST /pr/<owner>/<name>/<number>/drafts` — form fields `path`, `line`, `text`: adds your comment on a diff line to the pending review (see [Line comments](user-guide.md#line-comments)), or replaces the text of the one already on that line of the reviewed commit, so a double submit never makes two. Needs a done review of the PR head (409), a path and line as for the form (404, 400), and text that is not empty after trimming and at most 65536 characters (400); the 201st line comment of a PR returns 409, and so does a comment already posted. Answers 200 with the comment's block (its editor, `Remove from review`, its state) and, out of band, `Submit review (N)`; a refusal answers with the form again, text kept, and the error.
- `GET /pr/<owner>/<name>/<number>/diff/expand?path=<file>&from=<n>&to=<n>` — the lines of one gap of the diff (see [Diff view](user-guide.md#diff-view)) as context rows (HTML fragment, 200), read from the file at the reviewed commit with `gh api -H "Accept: application/vnd.github.raw+json" repos/<owner>/<name>/contents/<file>?ref=<sha>`. New numbers are `from..to`, `to=0` meaning the end of the file, clamped to the file's length; old numbers keep the offset of the next hunk, or that after the last hunk for the trailing gap. Expanded lines have no comment link. `path` must be a file of the PR with diff lines (unknown, removed or without a patch: 404); `from` and `to` must be positive numbers of at most 7 digits (`to` may be `0`) inside one gap of that file, `from` ≤ `to`, and `to=0` only for the trailing gap (400); a part of a gap is what is left around the unchanged lines the page already shows. A PR not on the dashboard returns 404, a review that is not done for the PR head 409. A file that is missing, binary or over 1 MiB, or a `gh` error, answers 200 with the row `Could not expand: <reason>`.
- `POST /pr/<owner>/<name>/<number>/points/<id>/checked` — form field `checked`, `1` to check the row and `0` to clear it; anything else returns 400. Answers 200 with the row's checkbox and, as an htmx out-of-band swap, the bar's `N of M checked`.
- `PUT /pr/<owner>/<name>/<number>/drafts/<id>` — form field `text`, the editor's text (autosaved 800 ms after typing stops). Creates the row's draft from the suggested comment if it has none; a text that differs from the stored one marks the draft edited, for good. Empty text is allowed; over 65536 characters returns 400. Answers 200 with the status `Saved` and, out of band, the row's state badge. For a line comment (`c<n>`), empty or whitespace-only text deletes it: the answer replaces the whole comment block (`HX-Retarget` to its diff block, or the details of its list row) with `Your comment on <file>:<line> was deleted.`, so its old editor cannot save over a later comment that reuses the id, and updates `Submit review (N)`. A line comment's editor also sends form fields `path` and `line`; for a `c<n>` id, a missing `path` or `line`, or one that differs from the comment's file and line, returns 404 and changes nothing (an editor left open in another tab after its comment was deleted cannot change a later comment that got the same id).
- `POST /pr/<owner>/<name>/<number>/drafts/<id>/include` — form field `include`, `1` (Add to review) or `0` (Remove from review); anything else returns 400. Including a row without a draft creates one with the suggested comment; including a draft whose text is empty after trimming returns 400 `comment text is empty`. For a line comment (`c<n>`), form fields `path` and `line` must match the comment's file and line, as for `PUT`, else 404. Answers 200 with the editor's buttons and, out of band, the row's state badge and `Submit review (N)`.

  For these three: the PR, result and id rules of the point endpoint apply (404), except that `PUT …/drafts/<id>` and `…/include` also take `c<n>` ids of line comments made on the reviewed commit (any other `c` id, such as one of an older commit, `c0` or `c01`, is 404); a posted comment returns 409 for `PUT` and `include`; a failed write of the pending file returns 500 and changes nothing. A 400, 409 or 500 answers with the same fragments showing the stored state (so a checkbox whose change failed shows the saved mark again, and the editor status says `Not saved`) and, out of band, the error at the bottom of the decision bar; a success clears it.
- `GET /pr/<owner>/<name>/<number>/review/summary?event=APPROVE|REQUEST_CHANGES|COMMENT` — the submit dialog as an HTML fragment (`text/html`, 200); a missing or empty `event` means `COMMENT`, any other value returns 400, a PR not on the dashboard 404. `body` is the summary text to show, so changing the decision keeps it. Every review state has the dialog (see [Submitting a review](user-guide.md#submitting-a-review)).
- `POST /pr/<owner>/<name>/<number>/review` — submits one GitHub review. Form fields `event`, `body` (the summary, at most 65536 characters), `rev` (the pending file's `rev` the dialog showed), `head` (the PR head the page showed), `expect` (the hash of the confirmation lines it showed) and `confirm` (`1` for "Approve anyway"). On success it answers 200 with `HX-Redirect: /pr/<owner>/<name>/<number>?submitted=<event>&n=<comments>`. A refusal or failure answers with the dialog again, showing the error with the summary kept: 400 for a bad event or a long summary, 409 for the checks in [Submitting a review](user-guide.md#submitting-a-review), 502 for a GitHub or `gh` failure, 500 when the review was posted but the pending file could not be saved. A PR not on the dashboard returns 404.
- `POST /pr/<owner>/<name>/<number>/threads/<id>/replies` — form field `text`: saves your reply to a GitHub review thread in the pending review, replacing the one already there (one per thread); empty or whitespace-only text deletes it. It writes nothing to GitHub: the reply is posted only with the submitted review (see [Discussions](user-guide.md#discussions)). `<id>` must be the id of one of this PR's threads as last fetched (fetched once if myReview has none, for example after a restart; over 200 characters or not found: 404, nothing written). A thread you cannot reply to (locked) returns 409 unless the text is empty, so a reply saved before the lock can still be discarded (`Discard reply`); text over 65536 characters returns 400; a failed thread fetch 502 with the error in the decision bar. Answers 200 with the thread block and, out of band, `Submit review (N)`. There is no stale-results check: replies belong to threads, not to a result.
- `POST /pr/<owner>/<name>/<number>/threads/<id>/resolve` — form field `resolved`, `1` (Resolve) or `0` (Unresolve); anything else returns 400. After the thread check of `…/replies` (404), it resolves or unresolves the thread on GitHub **right away** (`gh api graphql`, `resolveReviewThread` / `unresolveReviewThread`) and answers 200 with the thread block showing the state GitHub returned. From a diff-view line (form fields `row` and `row_threads`, set by the page) it instead answers with `HX-Reswap: none` and the line's two thread slots out of band, so the thread moves behind the line's `✓` icon or back under the line and the icon's count follows (the icon goes when no resolved thread is left). A `gh` error answers 502 with the error in the block.
- `POST /rerun` — form fields `repo` (`owner/name`), `number`, `filter` (the dashboard filter query, for example `mine=1&org=a`) and `from` (`details` returns to the details page). Queues a fresh review of the PR (see Re-run below), or starts the review of an on-demand PR, and redirects (303, or 200 with `HX-Redirect` for an htmx request with `from=details`, because the app's web view does not follow a 303) to `/?<filters>` when `filter` holds an active filter, re-encoded from the parsed filter parameters with the same rules as `GET /` (other parameters dropped, keys sorted, `risk` and `rec` deduplicated; the raw value is never copied into the redirect), to `/` when it holds none or does not parse, or `/pr/<owner>/<name>/<number>` when `from` is `details` (built from the validated PR, never from a client-supplied URL). A missing `repo` or a non-integer `number` returns 400; a PR not on the dashboard returns 404; a skipped PR returns 409 `pull request is skipped by rule skip[N]` and nothing is queued. With the header `HX-Request: true` (and no `from=details`), it answers 200 with that PR's dashboard row (the same `row` template as the list) and an out-of-band `<span id="pr-poll">` polling every 10 seconds with the re-encoded filter query; its errors keep the status codes above with a body of `<tr class="row-error"><td colspan="11"><p class="alert alert-error" role="alert">MESSAGE</p></td></tr>`, which `static/dashboard.js` swaps in for 4xx responses to `/rerun` only. `GET /rerun` returns 405.

`POST /comment` and `POST /approve` were removed with the submit dialog and return 404.

Unknown paths return 404.

Every response carries `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`, so the pages run only scripts and styles served by myReview itself (including the Wails runtime, `/wails/runtime.js`), cannot be framed, and submit forms only to myReview. Every response also carries `Cache-Control: no-store`: the app's web view would otherwise answer the live-refresh polls from its cache. A request other than `GET` or `HEAD` whose `Origin` header is present and not `wails://localhost` returns 403 `forbidden origin` and changes nothing (myReview's own htmx requests send no `Origin`).

### No TCP listener

myReview serves these endpoints only to its own window; nothing listens on a TCP port, so no other program or web page can reach them (the Host and cross-site checks of the web-server versions are gone). The window loads only myReview's own pages: `static/links.js` opens every link to another origin with the Wails runtime's `Browser.OpenURL` instead of following it, and the CSP's `form-action 'self'` keeps forms on myReview. As a backstop, whenever the window commits a page outside `wails://localhost/`, myReview loads the dashboard back into it and opens an `http(s)` URL in your default browser (any other scheme is dropped). The web view takes no drops, so a link or file dragged onto the window does not open (text cannot be dragged into a comment box either), and `window.open` and `target="_blank"` open nothing, because Wails provides no new-window handler. A foreign page that still loads for a moment cannot change anything: see the `Origin` rule above.

## Saved results

Every finished workflow (done or failed) is saved to `<MYREVIEW_DATA_DIR>/<repo#number, URL-escaped>.json`: repository, number, the head commit it reviewed, status, failed step and reason, the overview (`summary`), findings (each with `title`, `suggested_comment`, and `posted_url`, set only by earlier versions that posted single findings and now only read), `risk`, `recommendation`, `rationale` (array of strings), `points_of_interest` (array of `{"file","line","reason","title","suggested_comment"}`), the finish time, and the policy a done run applied: `threshold`, `threshold_source`, `sensitive_areas` (names) and `sensitive_areas_source`, each source `repository policy` or `default`.

- After a restart a pull request starts with its saved result. If the file is for an older commit than the current head, the result is outdated and follows the rules in [New commits and drafts](user-guide.md#new-commits-and-drafts), with the quiet period counted from startup: a ready PR is queued after `quiet_period`, a draft waits for Re-run. The file of an outdated result stays until the PR is queued. A PR with no usable file (none, a queued or running review when the app stopped, or a stale file as below) is treated like a new PR: queued, or on demand when older than `auto_review_max_age`.
- A `done` file whose `recommendation` is not `human review required` or `automated review is sufficient`, which includes every file saved before risk assessment existed, is not used: the PR is queued again silently (or on demand when older than `auto_review_max_age`). So is a `done` file without `threshold`, saved before repository policies existed. After such an upgrade, each open PR is therefore reviewed once more (three agent runs each). Queued and running workflows (including a re-run of a finished PR) are not saved, so they are queued again.
- A re-run deletes the PR's file. Files of closed or merged pull requests are deleted, but only after a successful fetch of their repository; a failed fetch, or `gh` missing or logged out, deletes nothing. Files of repositories no longer in the config are left alone.
- Writes go through a temp file and a rename, so a crash never leaves a half-written result.
- The directory is created with mode 0700 and files with 0600, because findings can describe security weaknesses.
- A corrupt or unreadable file is reported on stderr and ignored; the PR is reviewed again and the file replaced.
- Delete the result files to force a full re-review (deleting the directory also deletes the [run history](user-guide.md#ai-metrics)).
- Run one myReview instance per data directory.
- A file saved before titles and suggested comments existed loads unchanged, with both empty; the page then shows the fallbacks (see the details page), and nothing is reviewed again.
- `metrics` (done and failed runs) describes the run: `run_id` (random, new for every run), `queued_at`, `started_at`, `finished_at` (RFC 3339, UTC), `attempt` (1, plus one for each Re-run of the same head commit, kept across restarts), `diff_files`, `diff_bytes`, and `steps`, one per step that started (empty when the run failed at policy or prepare), in the order code review, security review, risk assessment. Each step has `step`, `agent`, `prompt_sha` (hex SHA-256 of the step's resolved prompt after Settings, `prompt_file` and `.myreview.json`; not of the PR, diff or findings blocks), `started_at`, `finished_at`, `wall_ms`, `status` (`done`, `failed`, or `cancelled` for a step stopped because its sibling failed or the run was dropped), `error_kind` (failed or cancelled only: `timeout`, `cancelled`, `not_found`, `exit`, `agent_error`, `bad_output` or `other`), `error` (the failure reason), `items` (findings, or areas plus points for risk assessment) and `usage`. `usage` is what the agent reported: `models` (per model: `model`, the four token counts and `cost_usd`), `api_ms`, `turns`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens` and `cost_usd`. Claude reports its models and an estimated list-price cost; codex reports tokens only, as model `codex default`, with no `cost_usd`. A step with no `usage` (killed by a timeout or cancellation, or an unreadable claude reply) has an unknown cost, not zero. Totals are not stored. A file saved before metrics existed loads unchanged, without `metrics`, and is not reviewed again.

## Output format

The agent must return exactly one JSON object. Each step passes its own JSON Schema to the CLI (both compiled in): the code review [`prompts/code-review.schema.json`](../prompts/code-review.schema.json), the security review [`prompts/findings.schema.json`](../prompts/findings.schema.json). Code review:

```json
{"summary": "Adds rate limiting to the login endpoint because ...", "findings": [{"severity": "High", "file": "internal/auth/login.go", "line": 42, "description": "...", "title": "Rate limit counter is never reset", "suggested_comment": "..."}]}
```

Security review: the same without `summary`.

- `summary` (code review only, required there): the overview, 2 to 5 sentences on what the PR changes and why; not blank; cut to 2000 characters when stored. In the security review output it is an unknown field;

- `severity`: exactly `Critical`, `High`, `Medium` or `Low`;
- `file`: a path relative to the checkout root. An absolute path under the checkout is made relative; an empty or absolute path, or one containing `..`, is invalid;
- `line`: an integer, 0 or more; `0` means the whole file;
- `description`: not empty; cut to 2000 characters when stored;
- `title`: a one-line title. Stored as its first non-empty line with whitespace collapsed, cut to 80 characters with `…`;
- `suggested_comment`: Markdown text for the PR author, ready to post on that line; cut to 2000 characters when stored;
- `title` and `suggested_comment` are required by the schema, but myReview accepts them absent or blank and stores them empty (the details page then falls back to the description);
- no other fields at any level. An empty `findings` array means no findings.

myReview validates the output itself. Anything else fails the step with `agent output is not in the findings format: <first problem>`. A non-zero exit fails it with `<agent> exited with status <n>: <end of stderr>`.

Risk assessment uses [`prompts/risk-assessment.schema.json`](../prompts/risk-assessment.schema.json):

```json
{"sensitive_areas": [{"area": "authentication", "file": "internal/auth/login.go", "line": 42, "reason": "...", "title": "...", "suggested_comment": "..."}],
 "points_of_interest": [{"file": "internal/db/migrate.go", "line": 0, "reason": "...", "title": "...", "suggested_comment": "..."}]}
```

- both arrays are required; empty arrays mean nothing touched and nothing extra;
- `area`: exactly one of the sensitive areas given in the input (case-sensitive). One entry per place; the same area may appear several times;
- `file` and `line`: the same rules as for findings;
- `reason`: not empty; cut to 2000 characters when stored;
- `title` and `suggested_comment` (a comment or question to the PR author about that place): the same rules as for findings; absent or blank, the details page falls back to the reason;
- no other fields at any level.

Anything else fails the step with `agent output is not in the risk assessment format: <first problem>`.

## Safety

- **Exact invocations.** myReview runs only these commands, with the binary looked up in `PATH`:

  ```sh
  claude -p --restricted --tools Read,Grep,Glob --strict-mcp-config --permission-prompts none \
    --output-format json --json-schema '<schema>'
  codex exec --sandbox read-only --ephemeral --skip-git-repo-check --ignore-user-config --ignore-rules \
    -c shell_environment_policy.inherit=core -c project_doc_max_bytes=0 --color never -C <tmp>/src \
    --output-schema <tmp>/<schema file> -o <tmp>/<step>.out.json --json -
  ```

  `<schema>` and `<schema file>` are the step's schema (see [Output format](#output-format)).

  Claude gets only the Read, Grep and Glob tools, confined to the checkout: no commands, no writes, no network, no MCP servers, and no user or project settings, so a PR cannot inject `.claude/settings.json` or hooks. Codex runs in its read-only sandbox (no writes, no network for commands) without your `config.toml` or rules, and without loading an `AGENTS.md` from the checkout as project instructions (`project_doc_max_bytes=0`), so a PR cannot steer it through that file. Permission-skipping or sandbox-bypass flags are never used.
- **No GitHub credentials.** The agent's environment is myReview's without `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN` and `GH_CONFIG_DIR`. myReview fetches the code with its own `gh` login; the checkout has no `.git`, remote or credentials.
- **Temporary checkout.** The checkout lives in a `myreview-*` temp directory that is removed when the workflow ends (done, failed or cancelled). Symlinks and other links in the tarball are skipped, so nothing in the checkout points outside it.
- **Process control.** Each agent runs in its own process group, killed on timeout, on Re-run and when the PR closes. Its stdout and stderr are capped at 1 MiB each, except codex's stdout: with `--json` it is a stream of JSONL events, read line by line, keeping only the token usage of `turn.completed` and the message of the last `turn.failed` or `error` event (a line over 64 KiB is discarded unparsed). Codex's final answer still comes from the `-o` file.
- **Codex read gap.** Codex's read-only sandbox can read any file your user can (for example `~/.ssh`), though it cannot write or use the network, so data could only leave through the finding text: the local dashboard and the model provider. Claude is confined to the checkout, which is why it is the default. Choose `codex` knowing this.
- **Limits** (constants, not configurable): diff 256 KiB, PR description 16 KiB, checkout 500 MiB, finding description and overview 2000 characters each.

Prompt injection in a PR (its code, title or description) can still distort the findings and the overview (for example a false "no findings"), and can make the risk agent under-report sensitive areas, which turns a PR that needs a human into "automated review is sufficient". Any High or Critical finding still forces human review, because myReview decides that itself. Injection cannot write files, reach the network or GitHub. Each PR costs three agent runs (code review, security review, risk assessment), with up to `concurrency` PRs at once, and there is no budget limit.

## Release

Releases are published in the public repository, [pythonrocks/my-review-tool](https://github.com/pythonrocks/my-review-tool), by `.github/workflows/release.yml` with [release-please](https://github.com/googleapis/release-please):

- conventional commits (`feat:`, `fix:`, …) on `main` feed a release pull request that bumps the version and updates `CHANGELOG.md`;
- merging that pull request tags `vX.Y.Z` and creates the GitHub release;
- the `dmg` job then builds the app from the tag, checks that its version equals the tag, and attaches `myReview.dmg` to the release.

For a local build, `make app && make dmg` still writes `bin/myReview.dmg`.

If the `dmg` job fails, use "Re-run failed jobs", not "Re-run all jobs": on a full re-run release-please sees that the release already exists, reports `release_created=false`, and the build is skipped. As a manual fallback, run `make app && make dmg` from a checkout of the tag, then `gh release upload vX.Y.Z bin/myReview.dmg --clobber --repo pythonrocks/my-review-tool`.

The DMG is unsigned (ad hoc signature only), so users need the Gatekeeper override from [Install](../README.md#install).

The app version is the nearest `v*` git tag without the `v` and without any `-suffix` (0.0.0 when there is none). The icon source is `build/appicon.png` (1024 px); `build/darwin/icons.icns` is made from it with `sips` and `iconutil`.
